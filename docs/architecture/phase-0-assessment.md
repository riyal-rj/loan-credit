## 1. Repository assessment

`E:\loan-credit` was an empty, non-git directory at the start of this engagement. There is no
pre-existing codebase, dependency set, database, or convention to preserve or migrate. This is a
**greenfield build**. Consequently:

- No conflicting architecture, legacy schema, or in-flight migration risk exists.
- The full technology baseline in the master instruction can be adopted from the first commit
  instead of being retrofitted.
- Git has been initialized (`git init`) so that branch protection, CODEOWNERS, commit history,
  and CI gates are meaningful from Phase 1A onward.

There is nothing to reject or renegotiate from an existing design. The gap is 100% of the target
system; the risk is scope, not conflict.

## 2. Confirmed use-case boundaries and explicit assumptions

The master instruction is exhaustive by design and describes a multi-quarter, multi-team system.
Building 100% of it (a live Kubernetes cluster, a live Temporal/Kafka/Qdrant/Keycloak/OpenBao
estate, a fine-tuned fairness pipeline, a signed-image supply chain, etc.) inside a single-operator
coding session is not achievable and claiming otherwise would violate the instruction's own
"never claim production-ready" and "no partial snippets" rules. The approach taken here is the one
the instruction itself prescribes in §25: **deliver in reviewable phases, each of which leaves the
repository runnable and tested**, and be explicit in every phase report about what is done,
conditionally accepted, or not yet started.

Explicit assumptions made to unblock work (documented so they can be challenged):

| # | Assumption | Rationale | Reopen if |
|---|---|---|---|
| A1 | One lending product for the initial slice: **unsecured consumer personal loan**, fixed term, fixed rate, single currency (USD), single jurisdiction (a synthetic "US-DEMO" jurisdiction, not a real US state/federal filing). | Smallest product that still exercises income, obligations, DTI, and term/rate policy branches without secured-collateral (LTV) complexity. | If the user wants a secured product (e.g., auto/mortgage) as the first slice. |
| A2 | Single-tenant-capable, multi-tenant-shaped from day one (tenant_id on every row/index/log from Phase 1B), but only one synthetic tenant (`demo-bank`) is seeded initially. | Multi-tenancy is a hard invariant (§5.8) — cheaper to bake in now than retrofit. | Never — this stays. |
| A3 | Local development runs on Docker Compose on a single Windows host with WSL2/Docker Desktop assumed available. Kubernetes manifests (Phase 10) are delivered as reviewable assets, not deployed to a live cluster, since no cluster is provisioned for this engagement. | No cluster credentials or cloud account provided. | If the user provides a target cluster/cloud account. |
| A4 | LLM stack defaults to local vLLM with an open-weight model behind LiteLLM; Groq/OpenAI adapters are wired but disabled by default (no keys present) until the user supplies them. | Matches §16 "must still run through local vLLM when hosted providers are disabled" and avoids taking any action against a real paid API without consent. | If the user supplies `GROQ_API_KEY`/`OPENAI_API_KEY` and asks to enable hosted routes. |
| A5 | CI engine for Phase 1A is a local, reproducible `make ci` target (lint/type/test/scan) rather than a live Tekton cluster, because Tekton needs a Kubernetes control plane that doesn't exist yet. A GitOps/Tekton pipeline definition is delivered as code in Phase 9/10 and documented via ADR-0004. | Avoids claiming a CI gate is "enforced" when no runner exists to enforce it. | Once a cluster/CI runner is available. |
| A6 | All applicant, document, bureau, KYC, employer, and transaction data is synthetic and generated by this build (Phase 2). No real personal data is ever accepted, per §4 non-goals. | Hard requirement, not negotiable. | Never. |

No blocking question prevents starting Phase 1A; assumptions above are reversible and documented
rather than gating.

## 3. Proposed target architecture and trust boundaries

Modular monolith (single deployable Python codebase, `src/finassist/`) with independently
scalable **process** boundaries (API, worker(s)), per §6.1 — not a microservice-per-bounded-context
split. Bounded contexts (§8) are enforced as **package boundaries with import-direction linting**,
not network boundaries, until a specific one earns its own service (documented via ADR when it
happens).

Trust boundaries (detailed threat model lives in `docs/threat-model/`, seeded in Phase 1A,
completed in Phase 9):

1. **Browser ↔ API edge** — untrusted. OIDC Authorization Code + PKCE (Keycloak, Phase 9); until
   then, Phase 1A ships auth as a pluggable port with a dev-only stub so downstream code never
   special-cases "auth is missing."
2. **API/workers ↔ PostgreSQL** — trusted service identity, tenant predicate mandatory on every
   query (RLS from Phase 1B).
3. **API/workers ↔ LLM gateway (LiteLLM)** — the *only* egress path to any model provider.
   Application code never imports a provider SDK.
4. **Workers ↔ synthetic external systems** (mock LOS/KYC/bureau/employer/core-banking) —
   untrusted-by-default response data (validated, never executed).
5. **Untrusted document/tool content ↔ LLM context** — treated as data, delimited, never
   concatenated into system instructions (§15, §16).

Dependency direction (enforced from Phase 1A via import-linter, see §22 of the instruction):
`domain` → nothing framework-specific; `application` → `domain` + `ports`; `infrastructure` →
implements `ports`; `api`/`worker` → composition root wires concrete infrastructure into
application services.

## 6. Phase 0 / Phase 1A acceptance criteria

**Phase 0 accepted when:** this document and the ADR set exist, assumptions are explicit, and the
technology matrix is traceable to §7 of the instruction. ✅ met by this commit.

**Phase 1A accepted when:**
- `uv sync` installs a locked dependency set.
- `uvicorn` boots the API from `apps/api/main.py` and `GET /health/live`, `GET /health/ready`,
  `GET /metrics` all respond correctly (readiness reflects real dependency checks, not a stub
  `True`).
- Settings fail fast (process exits non-zero) on invalid/missing required production configuration,
  verified by a test.
- Every log line is structured JSON with trace/correlation IDs when a request is in flight.
- OpenTelemetry spans are emitted for HTTP requests (verified via an in-memory exporter in tests,
  not by eyeballing).
- `apps/worker/main.py` boots independently, initializes the same settings/logging/telemetry
  stack, and exposes its own liveness endpoint.
- `make lint`, `make typecheck`, `make test` all pass with zero errors.
- No secret value is hard-coded; the dev secret provider reads from environment only, and
  `.env.example` documents every variable with no real values.
- Docker image builds, runs as non-root, and passes a local Trivy scan with no unresolved
  critical/high findings introduced by this phase's own dependencies.

## 7. Risks and blockers requiring user input

None are blocking Phase 1A start. Flagged for later phases:

- **R1 (Phase 6/9):** No Groq/OpenAI API keys provided. Hosted-model routes will be wired but left
  disabled until the user supplies keys and explicitly approves enabling them (this is also a
  policy requirement, not just a missing-credential issue).
- **R2 (Phase 10):** No Kubernetes cluster/cloud account provided. K8s/Helm/GitOps assets will be
  written and validated with `kubeconform`/`helm template` but not applied to a live cluster unless
  the user provides one.
- **R3 (Phase 2 onward):** Product/policy specifics (exact DTI thresholds, rate bands, term limits)
  for the synthetic "US-DEMO" policy pack are illustrative unless the user wants to model a specific
  real-world product's public rate sheet (still synthetic applicants, real published policy shape).
- **R4 (ongoing):** This is a single-operator build. The instruction's "coordinated team of ten
  roles" is applied as a review lens (each phase is checked against each role's concerns) rather
  than literally staffed; called out here so it isn't silently reinterpreted later.
